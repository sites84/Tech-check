Desenvolvedor consegue rodar Doom dentro de um banco de dados SQL

Um projeto engenhoso utiliza cerca de 1.300 linhas de consultas SQL para renderizar gráficos coloridos do clássico jogo Doom a taxas que alcançam até 35 quadros por segundo.

A famosa pergunta da comunidade de tecnologia sobre se um determinado dispositivo ou sistema é capaz de rodar o clássico jogo Doom ganhou mais um capítulo inusitado. Desta vez, o desenvolvedor Lukas Vogel conseguiu executar o jogo utilizando inteiramente um banco de dados SQL. A façanha foi detalhada em uma postagem de blog publicada no início de outubro de 2026, onde o criador admite que renderizar Doom em um banco de dados é uma ideia que desafia a lógica tradicional de programação.

Como funciona o SQLDoom

Para ser totalmente preciso, o projeto batizado de SQLDoom emprega um pequeno cliente escrito em Python cuja única função é gerenciar a entrada de comandos do usuário, controlar a temporização do jogo e exibir cada quadro gerado na tela. Por trás dessa interface simples, o trabalho pesado é realizado por uma série de tabelas do CedarDB que rastreiam a geometria e o estado atual do jogo. Cerca de 1.300 linhas de consultas SQL, distribuídas por 89 expressões de tabela comuns, implementam toda a lógica do jogo e geram quadros em formato bitmap a uma taxa impressionante.

Esta iniciativa representa uma evolucão massiva em relação a um projeto anterior do mesmo desenvolvedor, chamado DoomQL. No ano passado, o DoomQL tentou construir um jogo de tiro multijogador semelhante a Doom inteiramente em SQL, mas o resultado final limitou-se a gráficos ASCII em escala de cinza baseados em raycasting, lembrando mais os mapas simplificados de Wolfenstein 3D. Em contraste, o novo SQLDoom entrega quadros coloridos na resolução de 640 por 480 pixels, com uma fidelidade visual muito próxima ao executável original do jogo.

Convertendo WADs em tabelas relacionais

De acordo com o relato de Lukas Vogel, converter os arquivos WAD clássicos de Doom para um formato de banco de dados relacional foi um processo relativamente direto. Isso ocorreu devido à forma como o jogo original dividia seus níveis em vértices, linhas e setores. Até mesmo as famosas árvores de partição espacial binária do jogo puderam ser convertidas para SQL utilizando uma chave de ordenação pré-computada para cada posição no momento do carregamento dos dados.

Com essa estrutura configurada na tabela, um comando simples de ordenação consegue determinar a cada quadro quais partes das paredes devem ser exibidas e quais devem ser ignoradas, elevando consideravelmente o desempenho do sistema.

Ainda assim, houve desafios complexos na transição das tabelas SQL para a renderização de quadros em primeira pessoa. O maior obstáculo foi o algoritmo necessário para renderizar tetos e pisos, que não podiam aproveitar os métodos tradicionais baseados em colunas do jogo original. Para contornar isso, o SQLDoom recorre a uma abordagem alternativa descrita pelo autor como pouco ortodoxa, iterando sobre uma lista ordenada de painéis.

Desempenho e disponibilidade

Apesar da sobrecarga considerável gerada pelas operações constantes de leitura e escrita nas tabelas do SQL, o desenvolvedor relatou que conseguiu rodar o sistema a cerca de 60 quadros por segundo em um notebook equipado com um processador Ryzen 7, com quedas pontuais para 35 quadros por segundo em cenas mais movimentadas.

Para os entusiastas que desejam testar a novidade, todo o código-fonte está disponível no GitHub. O projeto requer uma cópia do CedarDB e um arquivo WAD original do Doom. Como alternativa, também é disponibilizada uma demonstração online gratuita para testes rápidos diretamente no navegador.

Por que isso importa

O projeto demonstra os limites operacionais de bancos de dados relacionais e tecnologias SQL, provando que estruturas de dados tradicionais podem ser adaptadas para processar lógica complexa em tempo real, como a renderização de gráficos de jogos eletrônicos.

O que pode acontecer no futuro

O uso de bancos de dados para gerenciar o estado de jogos pode inspirar novas abordagens no desenvolvimento de servidores multijogador, aproveitando recursos inerentes de concorrência e consistência de dados para evitar bugs físicos e inconsistências em partidas online.
